# Governed Reader Path Phase — Sprint 1 ADRs

## ADR-016 — Governed reader path and deterministic reader Worker

**Status:** Accepted by owner for Sprint 1 of the Governed Reader Path Phase. The acceptance date is recorded in the sprint closeout.

**Context:** ADR-011 and ADR-012 preserve and verify the bytes a task relies on. ADR-013 grounds a proposal against those bytes. ADR-014 records an independent human judgment. ADR-015 fixes limits for one reasoning attempt. Each was proven as a separate module called directly. None runs inside Core, no Worker has ever received captured bytes, and nothing has ever produced a proposal except by hand. Before any model reads a source, the path it will run on must exist and must be proven with a reader that has no judgment at all.

**Decision:**
1. A reader is a Worker whose only responsibility is to read the text it is given and return observations. It holds no authority. It cannot create a Task, create a child, retry, alter policy, alter Core, write to the ledger or the store, review or approve.
2. The first reader is deterministic. It reports each line of the form "Field: value" for the fields it was asked for, and reports a field it did not find as not found. It uses no model, provider, network or tool.
3. A reader runs only through one Core entry point, the reader path. The existing task path refuses a reader Worker, and the reader path refuses any other kind of Worker. Nothing else about the existing task path changes.
4. A reader task is one Task and one Snapshot under the existing lifecycle. Its task type is `read` in the domain `source-reading`. Its inputs are the requested fields and the capture references it reads, in ADR-012's canonical form. The same references are carried on the Snapshot and verified before execution under ADR-012.
5. Reader-only exception to ADR-012. ADR-012 is not amended. This ADR creates one explicit exception, governed by this ADR, to three ADR-012 decisions: decision 3 (references are not domain inputs and never enter a worker packet), decision 11 (references do not affect the task key) and decision 12 (the capture reference conflict). The exception applies only to a task of type `read` in the domain `source-reading` run on the reader path. For every other task, and for every provider Worker, ADR-012 controls exactly as before: references stay outside inputs, never enter a packet, do not affect the task key, the conflict rule applies, and references remain refused for provider Workers.
6. Under the exception, Core is the trusted host and selects the evidence. The evidence delivered is exactly the Snapshot's capture references: all of them and no others. The reader cannot choose a capture, add evidence, substitute evidence, or receive a path into the capture store, access to the filesystem, or access to the ledger. Core verifies each referenced receipt and its stored bytes before it builds the packet. For each reference the packet may carry only the capture id, the receipt hash, the content SHA-256, the size in bytes and the verified text; nothing else about a capture crosses the process boundary.
7. Task identity. The task key formula is unchanged. For a reader task the inputs it hashes include the capture references, so the task key identifies the requested fields together with the exact capture receipts, each by capture id and receipt hash. The same fields with a different receipt are a different task, including a second receipt for identical bytes. The same fields with the same set of receipts, supplied in any order, are the same task, and a repeat while that task is active is a duplicate submission. Because the evidence is part of identity, the ADR-012 conflict refusal cannot arise on the reader path and is not used there.
8. Trusted producer identity. The producer of a reader's proposal is the Worker identity in Ripley's trusted Worker descriptors, under a producer kind `worker`. Core sets it. A reader's output carries observations only; output that carries anything else, including a producer or a Snapshot identity, is refused.
9. This ADR revises ADR-013 decision 3 in one respect: a third producer kind, `worker`, exists. It is accepted only when Core assembles the proposal on the reader path. A proposal submitted directly to the public grounding function that claims the `worker` kind is rejected exactly as before, and the public function still accepts only `fixture` and `human`. No other part of ADR-013 changes.
10. Byte delivery. After the Snapshot's captures pass ADR-012 verification, Core reads each stored object once, confirms the size and SHA-256 of the bytes it read against the receipt, and confirms they are strict UTF-8. Those bytes are placed in the packet sent to the isolated process, each with its capture id, receipt hash, content SHA-256 and size. The isolated host checks the size and SHA-256 again before the reader sees the text. If any step fails, nothing is launched.
11. The reader is not given a path into the capture store, a ledger handle, a credential, provider authority or a network. This limits what it is handed. It is not a claim that the process is sandboxed: process isolation under ADR-009 is not a sandbox for hostile code, and the readers in this ADR are first-party code.
12. The delivered text is not copied into the ledger. The recorded request holds the identities, hashes and sizes of what was delivered. Quoted spans appear in the ledger only as part of a proposal under ADR-013.
13. Envelope. Core opens an ADR-015 attempt for the Snapshot before it launches the reader, with an input size Core computes itself: the total bytes of the delivered artifacts plus the bytes of the canonical inputs. The required budget is zero, because this reader costs nothing. If the envelope refuses, nothing is launched and no attempt is consumed.
14. Deadline. The envelope attempt's deadline is one absolute instant, fixed and recorded when the attempt is opened. It governs the whole attempt, including the preparation Core does after opening it. Immediately before launch Core reads the trusted current time and computes the remaining allowance: the deadline minus that time. If nothing remains, the reader is not launched; the attempt is closed as failed, the task is blocked at stage `timeout` with the message `deadline_expired_before_launch`, and the attempt stays consumed. If something remains, only that remainder is given to the ADR-009 isolation layer as the time the process may run. The original full duration is never given. The packet carries the same absolute deadline, and the isolated host's own watchdog acts only after that deadline plus its termination grace and margin, so the parent, whose wait ends at the deadline, reports the timeout; time spent preparing cannot turn an expired deadline into a host failure. ADR-015 supplies the absolute deadline and the accounting. ADR-009 enforces the remaining runtime. This ADR connects them for the reader path only.
15. Core closes the envelope attempt from what it observed: completed with the measured output size; failed when the process failed, was terminated and is known to have exited, or was never launched because the deadline had passed; uncertain when its exit could not be confirmed. The close time is the observed completion time.
16. A reader attempt whose close is not within limits is not grounded. An oversized output is recorded and goes no further.
17. Proposal admission. Core assembles the proposal from the Snapshot identity, the trusted producer and the reader's observations, and grounds it under ADR-013. A proposal that is rejected, whose evidence is blocked, or in which no observation is eligible for review, blocks the task. A proposal does not advance because an approved Worker produced it.
18. When grounding leaves at least one eligible observation, Core records a binding. It pins six records, each by id and by content hash: the Worker result, the proposal, the grounding validation, the envelope attempt, the envelope attempt's close, and the Snapshot. It also holds the task id, the execution attempt id, the SHA-256 of the proposal bytes and the producer: sixteen fields. The task then enters a new state, `awaiting_semantic_review`.
19. `awaiting_semantic_review` is durable: it survives a restart. In this sprint it has no exit. Nothing can move a reader task toward approval until a later decision in this phase defines how an ADR-014 semantic review and a human approval release it.
20. ADR-014 is unchanged. A semantic review of a reader's grounded proposal is made by a human whose label differs from the reader's Worker identity. In this sprint such a review can be recorded and changes no task state.
21. Human approval is the existing Core approval, reached through a bridge that this ADR does not define. A semantic review is never an approval and this ADR creates no automatic approval.
22. Failure outcomes. Each of these blocks the task with a recorded stage and no fallback: capture verification failed; evidence delivery failed; the envelope refused; the deadline passed before launch; the reader raised an error; the host failed, crashed or returned unusable output; the deadline was exceeded; the attempt closed outside limits; the reader's output was not observations only; the proposal was rejected; grounding was blocked; nothing was grounded.
23. One attempt. The reader path launches the reader at most once. There is no correction loop and no retry. A failed, uncertain, unclosed or never-launched attempt stays consumed under ADR-015.
24. Recovery. A reader task is not replayable. The existing recovery function refuses it and writes nothing. After a restart, an interrupted reader task is blocked by the existing restart rule and its consumed attempt stays consumed. An attempt that expired before launch is treated the same way: a restart restores nothing. A result that was recorded before an interruption remains in the ledger; continuing from it is not implemented and requires a later decision. No recovery step creates a Snapshot, a Task or an operation.
25. A new reader task for the same fields and captures, submitted by a person after an earlier one was blocked, is a new operation with its own Snapshot and its own single attempt, linked to the earlier task. This is permitted in this phase because the reader is local and costs nothing. It must be decided again before any reader that costs money.
26. Evidence chain. From the binding a reviewer can reach, by id and hash, the Worker result, the proposal, the grounding validation, the envelope attempt and its close, and the Snapshot, and from the Snapshot the capture receipts and the stored bytes. Integrity is never inferred from an id alone. Ripley provides a read-only check that follows a binding, confirms that each pinned record exists, is of the right kind and has the recorded hash, confirms that the records name one another consistently, and reports the first break it finds. The check writes nothing and does not re-read stored bytes; verifying bytes remains ADR-011's.
27. No model, provider, network, tool, child or agent is part of this ADR. ADR-010, ADR-011, ADR-014 and ADR-015 are unchanged. ADR-012 is unchanged except for the reader-only exception in decisions 5 to 7. ADR-013 is unchanged except for decision 9. The provider request, prompt, model and schema are unchanged.
28. This ADR does not prove: that a model can be run on this path; that a reader's reading is correct; that a hostile program is contained by the process boundary; that the amount a process writes to its output is bounded before it is measured; that a reviewer is who the label says; or that anything is approved.
29. Every failure stage named in decision 22 and every break the chain check can report must be produced by at least one test.

**Consequence:** Ripley has one governed path on which a component with no authority reads verified bytes and produces a proposal that Core grounds, binds and holds for human review. The component is a deterministic reader, so the path is proven without a model. A model-backed reader, the release from semantic review to approval, continuation after an interruption, a paid reader, capture references in any other Worker packet, and any other source format each require their own decision.
