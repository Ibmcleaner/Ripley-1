# Governed Reader Path Phase — Sprint 2 ADRs

## ADR-017 — Reader semantic release and explicit owner approval

**Status:** Accepted by owner for Sprint 2 of the Governed Reader Path Phase. The acceptance date is recorded in the sprint closeout.

**Context:** Under ADR-016 a reader task whose proposal grounds stops in `awaiting_semantic_review`, and that state has no exit. Under ADR-014 a human can record a semantic review of the grounded proposal, and that review changes nothing. No path leads from a reviewed proposal to an owner's decision, so the human gates are preserved only because nothing can pass them. This ADR defines that path without letting any step borrow authority from the one before it.

**Decision:**
1. Five acts stay distinct. A reader proposes. Grounding decides what the captured bytes support. An independent human semantic reviewer decides what is semantically acceptable. A separately invoked release decides whether the reviewed observations may be put before the owner. The owner approves or rejects. No act confers the authority of the next.
2. Release is one Core operation invoked by a person. The caller names one reader binding and one semantic review, each by record id and content hash, and gives a label for themselves. The caller supplies nothing else. Release creates no owner verdict.
3. Release derives the task from the binding and verifies, from ledger records alone and in this order: the binding exists, is a reader binding and has the given hash; the ADR-016 chain check verifies; the task it names is a reader task; the semantic review exists, is a semantic review and has the given hash; the review names the binding's grounding validation, proposal and Snapshot, each by id and hash; the review's criteria are the pinned ADR-014 criteria; the producer on the binding, on the proposal and in the review agree; the reviewer is a human label that differs from the producer without regard to case; at least one observation is eligible; the review's decisions cover every eligible observation exactly once, in proposal order, with the status and grounding verdict the records hold; and that review is the only semantic review of that validation.
4. If any of those checks fails, release is refused. A refusal is one recorded reason. It leaves the task state unchanged, creates no pending approval and creates no authority. The reasons are: `binding_unavailable`, `binding_hash_mismatch`, `chain_broken`, `task_unavailable`, `semantic_review_missing`, `semantic_review_wrong_kind`, `semantic_review_hash_mismatch`, `semantic_review_wrong_validation`, `semantic_review_wrong_proposal`, `semantic_review_wrong_snapshot`, `criteria_mismatch`, `producer_mismatch`, `reviewer_invalid`, `reviewer_is_producer`, `no_eligible_observations`, `decision_coverage_invalid`, `semantic_review_conflict`, `semantic_review_malformed`, `task_not_awaiting_review` and `release_conflict`.
5. Disposition. If every decision is acceptable, the disposition is eligible. If any decision is rejected, it is rejected. Otherwise, if any decision is needs_clarification, it is needs_clarification. Rejection takes precedence when both occur. Every decision the reviewer recorded, including unresolved issues, stays in the review record.
6. Approval scope. Core derives four lists of observation ids, in proposal order. Included: every eligible observation, when the disposition is eligible, and none otherwise. Uncertain: the included observations declared uncertain. Not found: the included observations declared not found. Excluded: every observation that was not grounded. The caller cannot choose, add to or remove from these lists. An excluded observation is never included and is never approved.
7. Release writes one immutable release record for either disposition. It pins the binding and the semantic review by id and hash, and holds the task, the producer, the reviewer, the label of the person who invoked the release, the disposition, the four lists, and the ids of the rejected and the needs_clarification observations.
8. Eligible. Release then writes a pending approval and moves the task from `awaiting_semantic_review` to `pending_owner_approval`. The pending approval is an approval record with the status `pending_reader_owner_approval`. It pins the release record by id and hash and carries the four lists. The order is: release record, pending approval, state change last.
9. Not eligible. Release moves the task from `awaiting_semantic_review` to `blocked`, with the disposition as the reason, and writes no pending approval. A rejected semantic review blocks the task; it is not an owner rejection. A blocked task is terminal. There is no clarification state, no revision, no second review and no automatic reread.
10. `awaiting_semantic_review` has exactly these two exits. No transition leads from it directly to approved or rejected.
11. The owner decision is a separate operation with its own entry point for reader tasks. The existing approval entry point accepts only a pending approval whose status is the existing one, so it refuses a reader pending approval for approval and for rejection. The reader entry point accepts only a pending approval whose status is `pending_reader_owner_approval`, so it refuses any other. Each refusal is an explicit check of the status, not an accident of a missing field. The existing approval operation is unchanged.
12. The reader owner decision requires the owner label, an explicit decision of approved or rejected, and a reason. Before it writes a judgment it derives every release fact again from the ledger, exactly as release does, and requires: that the derivation succeeds; that the disposition is eligible; that the stored release record equals what was derived; that the pending approval's four lists equal what was derived; that the pending approval pins that release record by id and hash; that the task has exactly one release record; and that the release has exactly one pending approval. A stored statement that a release is eligible is never trusted on its own. The decision does not reread captured bytes and does not run a reader.
13. A judgment is an approval record that supersedes the pending approval and carries its content, including the four lists, with the owner label, the decision and the reason. The task then moves from `pending_owner_approval` to approved or rejected.
14. Meaning of approval. The owner approves the exact reviewed eligible observation set identified by the release record as an acceptable reading of the captured evidence. Approval does not approve excluded observations, does not erase uncertainty, does not establish real-world truth, does not establish that the source is authentic, does not make a not-found observation proof of real-world absence, and authorizes no downstream execution or action in this phase.
15. Uncertainty declared by the reader stays declared in the proposal, the grounding validation, the semantic review, the release record, the pending approval and the judgment. Nothing in this ADR changes a status.
16. Repeat and interruption of release. Records written by an interrupted release grant no authority: the task has not left `awaiting_semantic_review`, and no decision can be made on it. An identical repeat of the call completes what is missing and writes nothing that already exists. A repeat never writes a second release record or a second pending approval. A call that names a different binding or review for a task that already has a release record is refused.
17. Repeat and interruption of the owner decision. If a judgment was written and the state change was not, an identical repeat finds the judgment, writes no second judgment and completes the state change. A repeat with the opposite decision is refused. A repeat after the state change returns the existing judgment and writes nothing.
18. Release and the owner decision create no Task, no Snapshot, no Worker attempt and no envelope reservation. They launch nothing.
19. ADR-016 decision 19 is revised in one respect: `awaiting_semantic_review` now has the two exits in decision 10. ADR-016 decision 21 named a bridge it did not define; this ADR defines it. ADR-016 decision 25, a person's new reader task after a block, is separate and unchanged. ADR-013, ADR-014 and ADR-015 are unchanged.
20. Limits. Labels are not authenticated identities; one person can use two labels. The ledger's transition table is not an authority boundary: code inside the process can append records and transitions directly. A task moved without a release has nothing that can be decided, and a hand-built release is decided only if every fact in it equals what Core derives from the evidence.
21. No model, provider, network, tool, child or agent is part of this ADR. The provider request, prompt, model and schema are unchanged.
22. Every refusal reason in decision 4, both negative dispositions, both cross-route refusals and every interruption point in decisions 16 and 17 must be produced by at least one test.

**Consequence:** A reader task can now reach an owner's decision, and only through grounding, one independent human semantic review, a recorded release and a separate explicit owner act. What the owner decides on is a bounded, enumerated set of observations with its uncertainty and its exclusions in view. Nothing follows from approval yet. Authenticated identities, a clarification or revision path, any consumer of an approved reading, and a model-backed reader each require their own decision.
