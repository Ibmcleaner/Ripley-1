# Governed Source Interpretation Phase — Sprint 1 ADRs

## ADR-013 — Proposal contract and grounding trust boundary

**Status:** Accepted by owner 2026-11-22. Implemented in Sprint 1 of the Governed Source Interpretation Phase.

**Context:** ADR-011 preserves the exact bytes of a source. ADR-012 ties a task's Snapshot to those bytes and verifies them before execution. Nothing yet governs a statement about what the bytes say. A later source reader will produce such statements, and its output cannot be trusted because it produced it. Ripley needs a contract for that output and a deterministic check that each statement points at bytes that really exist in the captured source, before any reader is built.

**Decision:**
1. A proposal is untrusted data. It is one UTF-8 JSON object, received as bytes, of at most 65,536 bytes. Its producer holds no authority. Nothing inside a proposal or a captured file is an instruction to Ripley.
2. A proposal names exactly one Snapshot by ledger record id. The Snapshot must exist and must carry at least one capture reference under ADR-012. The Snapshot's capture references are the only evidence a proposal may cite. A proposal cannot add evidence. A Snapshot may carry more than one capture reference; each is verified and a citation names one of them. This adds no source selection and no acquisition.
3. The schema is exact. A missing field or any additional field, at any level, rejects the whole proposal.
   - Proposal: `proposal_version` (the integer 1), `snapshot_id`, `producer`, `observations` (1 to 64).
   - Producer: `kind` ("fixture" or "human") and `identity` (1 to 128 characters: letters, digits, dot, underscore, colon, hyphen; first character a letter or digit). No model or worker producer kind exists under this ADR.
   - Observation: `observation_id` (1 to 64 characters: letters, digits, dot, underscore, hyphen; first character a letter or digit), `field` (1 to 128 characters), `status` ("asserted", "uncertain" or "not_found"), `value`, `citations` (0 to 8), and optionally `note` (1 to 512 characters).
   - For "asserted" and "uncertain", `value` is a string of at most 1,024 characters. For "not_found", `value` is null and `citations` is empty.
   - Citation: `capture_id`, `start`, `end`, `quote`.
   - `snapshot_id` and `capture_id` are strings of 1 to 64 characters. They are looked up, not parsed. An id that matches no suitable record fails where it is used.
   - `quote` is a non-empty string whose UTF-8 encoding is at most 4,096 bytes. Every string must be encodable as UTF-8. Lengths other than `quote` and the cited range are counted in characters.
4. A proposal is identified by its ledger record id and record hash. The SHA-256 of the received bytes is recorded as well. An observation is identified by the proposal record id together with its `observation_id`. An `observation_id` used twice rejects the whole proposal. It is not silently deduplicated.
5. `start` and `end` are integer byte offsets into the captured artifact, counted from zero. `start` is inclusive and `end` is exclusive. 0 ≤ start < end, and end − start is at most 4,096. Offsets count bytes, never characters.
6. A citation matches only when the artifact bytes from `start` up to `end` equal the UTF-8 encoding of `quote` exactly. Nothing is normalized: not case, not whitespace, not Unicode form, not line endings, not a byte-order mark.
7. An artifact is eligible only if it is at most 1,048,576 bytes and decodes in full as strict UTF-8. A citation whose `start` or `end` falls inside a multi-byte character fails.
8. Each citation is checked in this order and receives the first result that applies: `capture_not_on_snapshot`, `out_of_bounds`, `splits_character`, `quote_mismatch`, `matched`.
9. For each capture reference on the Snapshot, Ripley resolves the receipt, confirms it is a capture receipt, confirms its hash equals the reference's `receipt_hash`, reads the stored object once with a bounded read, and confirms that the size and SHA-256 of the bytes it read equal the receipt. Citations are evaluated against those same bytes in memory. The object is not read a second time. The validator runs inside Ripley. The caller supplies neither source bytes nor an object path and cannot substitute evidence. A proposal's producer never receives a path into the store.
10. Each reference receives one evidence result: `verified`, `receipt_missing`, `receipt_wrong_kind`, `receipt_hash_mismatch`, `artifact_too_large`, `artifact_unavailable`, `artifact_mismatched` or `artifact_not_utf8`. If any reference is not `verified`, no observation is evaluated, the outcome is `blocked_evidence`, and the result is not reviewable. There is no partial evaluation and no fallback.
11. Each observation receives one verdict: `grounded` when it has at least one citation and every citation matched; `not_grounded` with reason `citation_missing` or `citation_failed`; or `no_evidence_claimed` when its status is "not_found". The result of every citation is recorded.
12. Uncertainty is a declared status. An "uncertain" observation is grounded by the same rule as an "asserted" one, and its status and note are carried to the reviewer. Information the source does not support is declared as "not_found". Ripley does not compare `value` with `quote`.
13. Contradictory source content is reported as separate observations, each with its own citation. Ripley lists every field that has more than one observation. It does not choose between them.
14. Grounded is not semantically accepted. Grounding proves only that the proposal points at bytes that exist in the relied-upon captured source under these rules. It does not prove that the interpretation is correct, that the source is authentic, that the source is truthful, that the proposed fact is valid, or that anything is approved. No record or function under this ADR marks an observation as semantically accepted or approved.
15. Nothing from a proposal is stored until it passes, in this order: the size limit; UTF-8 decoding; strict JSON; the schema; the duplicate-id rule; and resolution of the Snapshot. Strict JSON means one object, with nothing after it but whitespace, no duplicate key at any nesting level, and no non-finite number, including NaN, either infinity and a number too large to represent. A proposal that fails leaves exactly one `grounding_rejection` record holding the SHA-256 of the received bytes, their size and one reason: `proposal_too_large`, `proposal_not_utf8`, `proposal_not_json`, `proposal_schema_invalid`, `duplicate_observation_id` or `snapshot_unavailable`. Its content is not stored.
16. A proposal that passes is stored as one `proposal` record. Its evaluation is stored as one separate `grounding_validation` record that pins the proposal record's hash and the Snapshot record's hash and holds the evidence results, the verdicts, the fields with more than one observation, the outcome and the review state. Grounding the same bytes twice creates two proposal records and two validation records with equivalent content. Nothing is deduplicated.
17. The human semantic-review package is derived from ledger records alone, is deterministic and writes nothing. It carries a fixed notice of what grounding does not prove, the producer, every observation with its status, value, note, verdict and citations, and the review state: `awaiting_semantic_review`, or `not_reviewable` when evidence was blocked. A `not_grounded` observation is shown and is marked not eligible for semantic review.
18. The producer's identity is recorded with the proposal. A semantic reviewer must be a human whose identity differs from the producer's. The review record and its enforcement require a later decision. Until then nothing can be semantically accepted.
19. Grounding does not change task state and writes no Result, Review, Evidence or Approval record. The validator is called directly and is not a step in the Core Task and Worker flow. Treating a proposal as a Worker Result requires its own decision.
20. No model, provider, network, tool, subprocess or child work is part of this ADR. The task key formula, ADR-010, ADR-011 and ADR-012 are unchanged.
21. This ADR applies the Doctrine's first priority, Security and Core Integrity, and the owner's rule that the engine must not grade its own homework: the component that will one day produce a proposal has no part in checking it.
22. Every evidence result, citation result, verdict reason and rejection reason named here must be produced by at least one test.

**Consequence:** Ripley can show, from the ledger and the store alone, which proposed observations point at real bytes of the captured source and which do not. It cannot yet show that any observation is correct. A source reader, a model-produced proposal, a semantic review record, value checking, other file types and any use of a provider each require their own decision.
